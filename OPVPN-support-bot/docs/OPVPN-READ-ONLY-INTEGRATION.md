# Подключение к данным OPVPN только для чтения

## Назначение и границы

Бот поддержки может по запросу пользователя прочитать его последние заказы и
сохранённое состояние оплаты. Доступ реализован в `support_bot/opvpn_readonly.py`.
Адаптер не импортирует код основного бота и не вызывает его изменяющие операции.

В этой версии разрешены четыре операции:

- `find_user_orders(telegram_id, limit)` — последние заказы аккаунта;
- `get_payment_status(telegram_id, order_id)` — состояние выбранного заказа,
  если он принадлежит этому аккаунту.
- `get_subscription_status(telegram_id)` — до пяти последних записей подписок
  аккаунта, включая тариф, статус, срок действия и лимиты устройств/трафика.
- `check_vpn_key(telegram_id, subscription_id)` — проверяет только наличие непустой
  записи VPN-ключа и срок подписки в локальной базе. Сам секрет не выбирается.

`telegram_id` берётся только из `RequestContext`, сформированного Telegram-обработчиком.
Модель не передаёт и не может переопределить его. В обоих SQL-запросах используется
условие `user_id = ?`; для статуса дополнительно проверяется `id = ?`. Параметры
передаются отдельно от SQL-текста.

## Какие данные возвращаются

Для списка заказов: ID, код тарифа, сумма, способ оплаты, сохранённый статус, дата
создания и дата оплаты. Для одного заказа: ID, сумма, способ оплаты, статус, даты,
а также булев признак `provisioning_issue`, показывающий только наличие ошибки выдачи.
Текст ошибки, `payment_id`, история попыток оплаты, URL счёта, промокод и VPN-ключ не
передаются модели. Для подписок выбираются только `id`, `plan_code`, `status`,
`expires_at`, `devices` и `traffic_gb`; поля `vpn_key`, `sub_url` и `panel_username`
не выбираются. Если запись помечена активной, но срок уже истёк, read-only запрос
отображает вычисленный статус `expired`, не меняя исходную запись. `check_vpn_key`
читает только булев признак непустого значения (`CASE` над полем `vpn_key`), а не
содержимое ключа. Это подтверждает сохранение значения в базе, но не его актуальность
в панели. Без внутреннего API поле `panel_status` равно `null`.

Статус читается из `orders` основной SQLite-базы. Это последнее состояние, сохранённое
самим OPVPN-ботом (например, после обработки вебхука или проверки в основном боте), а
не новый запрос к ЮKassa. Если в базе заказ `paid` и есть `provisioning_issue`, бот
должен передать случай специалисту и не говорить, что доступ выдан. Статус подписки
также читается только из SQLite и не подтверждает доступность VPN-клиента в панели.

### Прямая read-only проверка ЮKassa

Если в `.env` отдельного бота заданы `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`,
`get_payment_status` дополнительно выполняет только `GET /v3/payments/{payment_id}`.
Идентификаторы берутся из `payment_ids` / `payment_id` заказа только внутри backend;
перед вызовом проверяется, что заказ принадлежит Telegram ID пользователя. Проверяются
статус `succeeded`, признак `paid`, валюта RUB и сумма не меньше актуальной суммы заказа.
При сетевой ошибке результат будет `unknown` и обращение передаётся специалисту, а не
объявляется неоплаченным.

DeepSeek получает только статусы, суммы, даты, число проверенных платежей и результат
сверки. ID платежей, API-ключ, URL платежа и исходный ответ ЮKassa модели не передаются.
В клиенте реализован только GET-метод — без создания, отмены или возврата платежей.
Учётные данные хранятся в `.env` на сервере и не должны попадать в Telegram или запросы
к ИИ.

Для включения прямой проверки заполните в `.env` отдельного бота обе переменные
`YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`. При заполнении только одной приложение
не запустится. Если они пусты, используется только статус из базы. Реальные значения
не помещайте в `.env.example` и не присылайте в чат.

Входящие сообщения маскируются до сохранения и передачи модели: фильтр распознаёт VPN URI,
Telegram-токены, JWT, значения у полей с именами `*_API_KEY`, `*_SECRET`, `*_TOKEN`,
`*_PASSWORD`, bearer-токены и номера карт, проходящие проверку Luhn. Фильтр также стоит
внутри движка прямо перед моделью. Это снижает риск случайной отправки распознаваемых
секретов, но не распознаёт произвольный секрет без маркера или известного формата; поэтому
не следует отправлять секретные значения в поддержку.

## Настройка локального запуска

В `.env` отдельного бота укажите абсолютный путь к основной базе:

```dotenv
OPVPN_DB_PATH=E:/path/to/opvpn/data/opvpnbot.sqlite3
```

На Windows допустим обычный абсолютный путь с прямыми слешами (`E:/path/to/...`). При пустом
`OPVPN_DB_PATH` проверки заказов и оплат не предлагаются ИИ; создание тикетов продолжает
работать. Если путь задан, но файл или необходимые поля таблиц `orders` и
`subscriptions` недоступны, запуск завершается
ошибкой, чтобы конфигурационная проблема не выглядела как отсутствие заказов.

SQLite открывается с `mode=ro` и `PRAGMA query_only=ON`. Не указывайте путь к базе
поддержки вместо базы OPVPN.

## Настройка Docker / сервера

База основного бота находится в `/app/data/opvpnbot.sqlite3` внутри его контейнера.
Для отдельного контейнера поддержки нужно предоставить тот же каталог данных как
read-only volume и задать `OPVPN_DB_PATH` на путь внутри контейнера поддержки.
Не подключайте поддержку к новому или пустому файлу базы.

Основной бот использует SQLite WAL. При read-only подключении каталог должен содержать
актуальные WAL/SHM файлы, когда они требуются SQLite. Проверьте чтение на целевом способе
монтирования до запуска поддержки в рабочем режиме. Если хостинг не умеет безопасно
предоставить живой WAL-каталог read-only, следующий шаг — небольшой внутренний
аутентифицированный read-only API в основном боте; включать запись или передавать файл
базы через копирование во время работы нельзя.

## Добавление новых возможностей

Новые методы подключать в том же read-only адаптере отдельными запросами с обязательной
проверкой владельца. Возвращаемую проекцию полей нужно держать минимальной. Запросы к
панели, повторная выдача, отмена платежа и любые другие изменяющие действия этой
интеграцией не разрешены. Перед подключением подписок или диагностики панели нужно
отдельно описать их источник истины, проверку владельца и обработку чувствительных
данных.

## Внутренний endpoint статуса клиента в панели

3x-ui API-токен является полномочным администраторским credential, поэтому его нельзя
копировать в отдельный бот поддержки. Это следует из [официальной справки по API
3x-ui](https://github.com/MHSanaei/3x-ui/blob/main/docs/content/docs/en/reference/api/index.mdx).
Клиент поддержки подготовлен в `support_bot/panel_status_client.py`, но endpoint
основного бота пока не реализован. Поэтому `check_vpn_key` доступен только как проверка
локальной записи; live-статус панели и прямые запросы к 3x-ui не включены.

Предлагаемый контракт endpoint:

```text
GET /internal/support/subscriptions/{subscription_id}/panel-status?telegram_id={id}
Authorization: Bearer <отдельный scoped token>
```

Основной бот должен повторно проверить, что `subscriptions.id` принадлежит переданному
`telegram_id`, затем вызвать только read-only проверку панели. Endpoint возвращает только
безопасные поля, исключая `vpn_key`, `sub_url`, `panel_username`, полные объекты клиента
и сырые ответы панели. Допустимая форма ответа:

```json
{
  "ok": true,
  "data": {
    "status": "enabled",
    "panel_reachable": true,
    "expires_at": "2026-12-31T00:00:00+00:00"
  }
}
```

`status` ограничен значениями `enabled`, `disabled`, `expired`, `not_found` и `unknown`.
На сетевой ошибке endpoint отвечает безопасной ошибкой без тела ответа панели; клиент
поддержки передаст обращение специалисту. API использует отдельный scoped token, не
токен 3x-ui. `OPVPN_PANEL_STATUS_API_URL` принимает HTTPS; HTTP разрешён только для
loopback-разработки. URL и токен должны быть заданы вместе, иначе инструмент отключён.
