# Runbook оператора OPVPN

Что делать дежурному, когда что-то ломается. Все команды — для варианта с systemd;
для Docker замените на `docker compose logs/restart`.

## 0. Быстрая диагностика (30 секунд)

```bash
curl -fsS http://127.0.0.1:8081/healthz     # {"ok":true,"db":"ok","version":"2.0.0","build":"2.0.0-8-g1a2b3c4"}
systemctl status opvpnbot                    # запущен/рестартует?
journalctl -u opvpnbot -n 200                # последние строки логов
```

- Поле `build` в `/healthz` — какая именно сборка запущена (тег/коммит); помогает сразу
  понять, что деплой не применился. Там же `version` (semver).

- Полный лог — `data/bot.log` (с ротацией). Каждая строка содержит `rid=…` —
  короткий id конкретного действия. Найти всё по одному инциденту:
  `grep 'rid=1a2b3c4d' data/bot.log` (rid продублирован админу в сообщении об ошибке).

## 1. Бот не отвечает

1. `systemctl restart opvpnbot` (или `docker compose restart`).
2. Если падает при старте — в логе будет блок «Проблемы конфигурации»: исправьте `.env` и перезапустите.
   Служба при этом **не перезапускается сама** (`RestartPreventExitStatus=2` в юните: код 2 = ошибка
   конфигурации, рестарты бы только заспамливали лог) и в `systemctl status` видна как `failed`.
   Если systemd успел упереться в лимит запусков («start request repeated too quickly»),
   перед перезапуском выполните `sudo systemctl reset-failed opvpnbot`.
3. Проверьте, что запущен ровно один процесс: в логе одна строка `Start polling`
   (или `Апдейты Telegram: вебхук …` в режиме вебхука); см. также раздел 3a.
4. Docker: `docker compose up -d --build`.

Профилактика: `Restart=always` (systemd) / `restart: unless-stopped` (compose) + внешний
монитор на `/healthz` (см. README → «Мониторинг и CI»).

### Ошибка «TelegramNetworkError: HTTP Client says - Request timeout error»

Это **не баг кода**, а сетевой сбой: HTTP-запрос к `api.telegram.org` не дождался
ответа за отведённое время (тормозит канал до Telegram, сам API, либо прокси/VPS).
Единичные эпизоды — норма: polling сам переживает сбои с backoff, а `ErrorsMiddleware`
теперь такие ошибки только логирует (не будит админов пачками).

Диагностика и лечение:

1. Найти эпизоды по rid из уведомления: `grep 5f32b0f2 data/bot.log`.
2. Проверить сеть с сервера: `curl -sv -o /dev/null -w '%{time_total}\n' https://api.telegram.org` —
   если дольше ~10–20 с или соединения рвутся, чинить канал/DNS/MTU/фаервол, а не бота.
3. Если таймауты случаются при медленном, но рабочем канале — увеличить лимит в `.env`:
   `TG_REQUEST_TIMEOUT=90` (или 120) и перезапустить службу. Значение применяется к
   HTTP-сессии aiogram (`AiohttpSession(timeout=...)`) при старте бота.

## 1a. Перезапуск из админки

В боте: `/admin` → **«🔧 Обслуживание»**:

- **🔄 Перезапустить бота** — бот мягко завершится, служба поднимет его за пару секунд
  (требует `Restart=always`, что в юните по умолчанию);
- **♻️ Перезапустить Xray** — ядро панели 3x-ui перезапускается через её API
  (`POST /panel/api/server/restartXrayService`); активные соединения клиентов на пару
  секунд оборвутся и переподключатся сами.

Обе кнопки — с подтверждением. Саму панель (`x-ui`) из бота не перезапустить (бот ходит
в тот же процесс) — только вручную: `sudo systemctl restart x-ui`.

## 2. Панель 3x-ui недоступна → не выдаются ключи

**Симптомы:** пользователю «Не удалось выдать…», админам «🚨 Оплата прошла, но выдача не удалась».

1. `/admin` → «🧪 Проверить панель».
2. Доступность панели с сервера: `curl -sS "$XUI_URL/panel/api/server/status"`.
3. **TLS:** если панель на HTTPS с self-signed сертификатом — задайте `XUI_CA_FILE` (PEM) либо
   (менее безопасно) `XUI_VERIFY_SSL=false`. При старте в логе есть строка `3x-ui TLS: …`.
4. Проверьте, что `XUI_INBOUND_IDS` существуют (Inbounds в панели).
5. **Оплаченный заказ:** он уже в статусе `paid`, поэтому повторный «Подтвердить» не сработает.
   Выдайте подписку вручную: `/admin` → «👥 Пользователи» → карточка → выдать.

## 3. Платежи: вебхук / ЮKassa

**Симптомы:** вебхук 504/503, «Проверить оплату» падает, деньги списаны — доступ не выдан.

1. Доступность ЮKassa из VPS: `curl -4 -sS https://api.yookassa.ru/v3/me`.
   Если IPv6 «полуживой» (типовой случай) — задайте `PAYMENTS_PROXY` (HTTP-прокси).
2. Вебхук отклоняется с `403`: включите `WEBHOOK_TRUST_PROXY=true` и передавайте `X-Forwarded-For`
   из nginx; `proxy_read_timeout 30s`, `proxy_http_version 1.1`.
3. Если вебхук не приходит — сработает резервный опрос раз в 3 минуты либо кнопка «🔄 Проверить оплату».
4. Ручное подтверждение: `/admin` → заказы → «✅ Подтвердить».
5. Сверьте статус и сумму в кабинете ЮKassa (бот сверяет сумму ±0.01 ₽).
6. Алерт «⚠️ Двойная оплата заказа #N» — по одному заказу прошло два разных платежа (деньги списаны дважды).
   Проверьте оба платежа в кабинете и верните лишний (авто-возврата в боте нет).
7. Алерт «🔎 Платёж … восстановлен и привязан к заказу #N» — счёт ранее был потерян
   (`payment_id` перезаписывался до версии с `orders.payment_ids`). Оплата зачтена: убедитесь, что период выдан.

## 3a. Апдейты Telegram: вебхук или long-polling

Режим виден в логе при старте: `Апдейты Telegram: вебхук https://…` либо `Start polling`.

```bash
# Что видит Telegram: адрес вебхука, очередь и последняя ошибка доставки
curl -s "https://api.telegram.org/bot<TG_TOKEN>/getWebhookInfo" | python3 -m json.tool
```

- **Бот не отвечает, в логе `Conflict: can't use getUpdates method while webhook is active`** —
  остался вебхук с прошлой конфигурации, а бот запущен в режиме polling. Снять вручную:
  `curl -s https://api.telegram.org/bot<TG_TOKEN>/deleteWebhook` (бот делает то же самое
  при старте в polling-режиме, но перезапуск мог случиться раньше правки `.env`).
- **»в `getWebhookInfo` растёт `pending_update_count`** — апдейты не доставляются: домен не
  резолвится, сертификат просрочен или nginx отдаёт 4xx/5xx на пути `TG_WEBHOOK_URL`.
  Проверка: `curl -i -X POST https://<домен><путь> -d '{}'` — ожидается 403
  (запрос без заголовка `X-Telegram-Bot-Api-Secret-Token`).
- **В логе «Апдейт Telegram отклонён: неверный secret token»** — заголовок не доходит до бота
  (прокси съел его) или `TG_WEBHOOK_SECRET` в `.env` не совпадает с тем, что зарегистрирован.
  Лечение: перезапустить бота — он заново вызовет `setWebhook` с текущим секретом.
- **С `set_webhook` не сложилось** (log: «работаю через long-polling») — Telegram требует
  HTTPS с валидным сертификатом: проверьте `TG_WEBHOOK_URL` и домен. Бот сам откатился
  на polling, апдейты не теряются.
- **Возврат на long-polling:** `TG_WEBHOOK_ENABLED=false` в `.env` + перезапуск.
- **Гарантия доставки:** при `TG_WEBHOOK_FAST_ACK=true` Telegram получает 200 сразу, обработка
  идёт в фоне; на остановке бота фоновые апдейты дожидаются (в логе — «Дожидаюсь обработки
  принятых апдейтов»). Если процесс убит жёстко (SIGKILL), такой апдейт теряется — но оплата
  не пропадёт: заказ доберёт `poll_yookassa_orders` или кнопка «🔄 Проверить оплату».

## 4. Подписка не импортируется в клиент (3x-ui)

- Пустой ответ `404` при открытии ссылки подписки → у клиента `limitHwid > 0` (HWID-гейт 3x-ui).
  Бот создаёт клиентов с `limitHwid=0`; «лечится» продлением из бота или в панели.
- Ссылка = `XUI_SUB_BASE/{subId}`. Проверьте, что подписочный сервер панели включён и доступен.

## 5. БД, бэкапы, восстановление

- Бэкапы: `data/backups/opvpnbot-*.sqlite3` (каждые `BACKUP_INTERVAL_MINUTES`, хранится `BACKUP_KEEP`).
- Ручной бэкап админу: `/admin` → «💾 Бэкап».
- Восстановление: остановите бота → замените `data/opvpnbot.sqlite3` → удалите `-wal`/`-shm` → запустите.

## 6. Дубли выдачи/сообщений

- Заказ завершается ровно один раз (`claim_order_for_payment`), повторная выдача невозможна.
- Если видите дубли — проверьте, что не запущено два процесса (в логе один `Start polling`),
  затем проследите инцидент по `rid`.

## 7. Обновление

```bash
# systemd
cd /srv/opvpnbot && git pull && sudo bash install.sh --update
# Docker
git pull && docker compose up -d --build
```

Перед обновлением сделайте бэкап. CI (`.github/workflows/ci.yml`) прогонит линт, тесты и аудит зависимостей.

## 8. Регламент (раз в неделю)

- `/healthz` отвечает; внешний монитор без алертов.
- Ошибки в логе: `grep ' ERROR ' data/bot.log | tail`.
- Свободное место под `data/` (БД + бэкапы).
- CI зелёный (последний push/PR).

## 9. nginx, сертификат, firewall

Настраивается установщиком: `sudo bash install.sh --domain <домен> --email <адрес>`.

- Конфиг сайта: `/etc/nginx/sites-available/opvpnbot` — **генерируется** из
  [`deploy/nginx/opvpnbot.conf.tmpl`](../deploy/nginx/opvpnbot.conf.tmpl); не правьте копию вручную,
  правьте шаблон и перезапустите `install.sh` (старый файл сохраняется рядом как `*.bak.<дата>`).
- Продление сертификата — автоматом (пакет `certbot` ставит systemd-таймер). Проверка вручную:
  `sudo certbot renew --dry-run`; показать сертификаты: `sudo certbot certificates`.
- Забыли e-mail или домен сменился — просто повторно запустите
  `sudo bash install.sh --domain <новый домен> --email <адрес> --update`.
- **firewall (ufw)**: включён установщиком; SSH-порт определяется автоматически и открывается ДО
  включения. Посмотреть: `sudo ufw status verbose`. Если доступ к серверу пропал — спасаться через
  консоль провайдера: `sudo ufw allow <порт_ssh>/tcp && sudo ufw reload`.
- Бот за nginx слушает вебхук только на петле (`WEBHOOK_HOST=127.0.0.1`) — порты 8080/8081 снаружи
  закрыты, ломать ничего не надо. При отладке: `curl -fsS http://127.0.0.1:8081/healthz`.
- Проверка всей цепочки: `curl -fsS https://<домен>/healthz` и тестовое уведомление из кабинета ЮKassa
  (должно прийти без ошибок в `journalctl -u opvpnbot`).
